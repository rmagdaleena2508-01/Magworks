Financial Advisory Agents

Two AI agents for a wealth-advisory platform — one plans debt payoff, one finds life-insurance coverage gaps. Deterministic Python does every calculation; the LLM only reasons and explains, never estimates a number.

Code
Internship build · 2 agents · 5 tools · 30 passing unit tests

The brief

Built as an AI-engineer intern at Upstride, for a multi-agent financial-advisory platform. I owned two of the agents end to end and shipped 5 tools across them, with 30 passing unit tests.

The Debt Management Agent has three tools: a payoff optimiser (avalanche vs snowball, with month-by-month amortisation), a consolidation analyser (net savings after fees, plus a behavioural warning), and a credit-score improvement planner (CIBIL factor weights → a prioritised plan). The Insurance Coverage Gap Analyzer sizes the coverage a person actually needs (the DIME method — debt, income, mortgage, education), compares it to their existing cover, and returns the gap, a risk level, and a hand-off signal.

How every tool was built

The same sequence for each tool, every time: a Pydantic schema for the inputs and outputs → a pure Python function with no LLM in it → unit tests, all green, before anything was wired → a CrewAI @tool wrapper → the agent assembly (role, goal, backstory, guardrails) → an end-to-end run with mock users.

One rule held throughout, and it's the thesis of the whole project: the LLM never does the math. Every number comes from a deterministic Python function, so the output is testable and can't drift.

The two bugs that shaped the design

  • The LLM reads the docstring, not the type annotation. A tool typed as debts: list[dict] made the model call it with empty dicts every single time; Pydantic rejected it, the model retried the same broken input, and it hit max_iter. The fix: take a JSON string and put a full concrete example — every field named — in the docstring, then json.loads it inside the wrapper. For nested inputs, a worked example beats a type.
  • Never trust the LLM to carry a number between tools. The insurance agent had two tools; the model was meant to pass the required-coverage figure from the first into the second, and instead passed 0 — classifying a critically under-insured user as over-insured. Rewriting the prompt with explicit steps and warnings made it better, not reliable. The real fix was to merge the two tools into one wrapper that takes the raw inputs and runs the DIME sizing and the gap analysis together in Python, so nothing crosses the LLM mid-calculation. That became a short white paper: single-wrapper tool architecture over chained LLM calls.

What I took from it

  • State between tool calls is an engineering problem. Fix it in Python, not in the prompt — if two steps are logically sequential and the second depends on the first's number, make them one tool.
  • Tests before wiring. Every tool had passing unit tests before it ever touched the agent layer, so a wrong answer was always a logic bug, never a mystery.
  • Honest numbers only. Claims are scope-based ("3 tools, 17 tests"), never invented percentages — and I confirmed the scope with the PM against the source doc before writing any code.
  • Treat a blocked secret as a real incident. A live API key once slipped into .env.example on the public repo; GitHub push protection caught it, and I rotated the key rather than just removing the line. Examples get placeholders, always.
